# Prototyping: Alpha to Beta

**Looks-like/works-like ladders — alpha goals, beta expectations, timeline discipline, and test-refine loops.**

<a id="the-intuition"></a>
## 1. The Intuition

::: callout-intuition Core Mental Model: Dress Rehearsals, Two Nights
**Alpha** (in-house shakedown: does it *work* at all? — looks-like *or* works-like separately allowed! rough edges expected!). **Beta** (friendly-users premiere: does it work *for them*? — feature-near-complete, feedback-hungry!). **Transition design→prototype** (what fidelity answers which question! — fidelity matched to unknowns!). **Timelines** (buffered milestones, long-lead orders first!). **Alpha-test-refine loops** (break→learn→fix cycles *before* beta eyes!). **Beta transition** (selection/support/telemetry planning — friendly, not random, users!).
:::

::: anim pilot-ladder Climb with Questions
PoC asks risk, alpha asks works, beta asks users, pilot asks scale — each rung pricier, each answer narrower.
:::

<a id="the-math"></a>
## 2. Theoretical Framework & Formalism

### 2.1 Prototype ladder + transition + timeline + beta ops

* Alpha (internal, rough, works-questions!) → beta (external-friendly, near-complete, user-questions!) — fidelity-per-question matching!
* Transition triggers (PoC-verdicts in! SRD baselined!).
* Timeline tactics (critical-path builds first! long-lead procurement early! buffer honesty — student teams pad $30\%$+!).
* Beta ops (cohort selection! support channels! telemetry consent! feedback cadence! → transition criteria to pilot!).

::: callout-formula KTU Formula Vault: Rehearsals
Alpha (**works?**) · beta (**for-users?**) · fidelity **per-question** · buffers **honest**.
:::

::: callout-pitfall Beta-as-Launch (Premiere Confused with Opening Night!)
Beta-labeled selling (paying users, no support plan, unmeasured!) burns trust (first-impression scars!) — beta gates (support/telemetry/rollback ready!) before externals touch. Premiere discipline (friendly-selected, supported, measured!) vs launch readiness separated.
:::

<a id="worked-example"></a>
## 3. Worked Example / Step-by-Step Scenario

::: step [Step 1: Setup] Formulating the Problem
"QR-token unit: (a) alpha scope + $3$ test questions? (b) Beta cohort + support plan? (c) $4$-week timeline with buffers? (d) Beta→pilot gate criteria?"
:::

::: step [Step 2: Execution] Rehearsal Plan
1. (a) Scope: single counter, staff-operated (works-like over looks-like!) — Qs: scan-rate? readability-noon? fallback-time?
2. (b) Cohort: $2$ friendly counters (trained cashiers!) + support WhatsApp + daily log review (telemetry: scans/errors/times!).
3. (c) Wk1 build (+buffer $3$d for display shipment!) → Wk2 alpha trials → Wk3 fixes → Wk4 beta (buffered, long-lead first!).
4. (d) Gates: scan-rate $\ge95\%$ + fallback $<30$s + cashier approval (all three, no waivers!).
:::

::: step [Step 3: Conclusion] Final Result
Scope-per-question, cohort-with-support, buffered timeline, gated transition. Gate-criteria pre-set (beta→pilot bars published!) prevents premiere-drift.
:::

## 4. Active Recall Quizzes

::: quiz Q1: Foundational Concept
Looks-like vs works-like split prototyping economises by:
(A) Doubling work always
(*B) Question-matched fidelity (aesthetics questions need foam, not circuits!; function questions need breadboards, not polish! — fidelity spent only where the question lives!)
(C) Designer preferences
(D) Tool limitations
::: explanation
Fidelity-targeting (question dictates finish!) avoids overbuilt probes (polished circuits answering look-questions expensively!). Question-matched spend (cheap probes, dear answers!) is the prototyping economy.
:::

::: quiz Q2: Foundational Concept
Beta cohort *friendly-selected* (not random public) since:
(A) Elitism
(*B) Feedback quality + supportability (forgiving, communicative, reachable users give *diagnostic* feedback!; random public gives ratings + rage!) — learning-optimised sampling (insight per user maximized!)
(C) Marketing seeding
(D) Easier NDAs
::: explanation
Diagnostic-density sampling (articulate, tolerant, observable users!) over representativeness (that's pilot's job!). Learning-per-user metric (insights/user!) picks cohorts — beta optimises learning, pilot representativeness.
:::

::: quiz Q3: Foundational Concept
Telemetry-consented beta instrumentation needs consent because:
(A) Storage costs
(*B) Behavioural data sensitivity (usage patterns identify!; trust contract with friendly users!) — consent + minimization + retention limits (ethics operationalised, not appended!)
(C) Slows devices
(D) Regulators never check (they might! — plus trust economics!)
::: explanation
Friendly-user trust (beta bargain: access for honesty *both ways*!) — consent/minimization/retention as contract terms. Ethics-instrumented (not ethics-mentioned!) beta ops.
:::
