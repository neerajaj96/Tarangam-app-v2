<a id="worked-example"></a>
## 3. Worked Example / Step-by-Step Scenario

::: step [Step 1: Setup] Formulating the Problem
"Lab queue chaos (shared 3D-printer!): POV + success/non-goals + one empathy tool pick with why + phase plan (week!)."
:::

::: step [Step 2: Execution] Sprint Answers
1. POV: "Project teams need *predictable* print slots because deadline weeks collide, not filament." (need-because contract!).
2. Success: booking-show rate $>90\%$ + max-wait $24$h in $3$ weeks; non-goal: buying printers!
3. Tool: journey map first (queue pain is *temporal* — curves show it!; empathy map second for repeat offenders!).
4. Week: $2$-day empathize (stakeouts!), $1$-day define, $2$-day ideate, $2$-day prototype (paper booking!), rest test (one-lab pilot!).
:::

::: step [Step 3: Conclusion] Final Result
POV-contract, metric-gates, tool-matched-to-pain-type, phased week. Tool-pain matching (temporal→journey!) shows diagnostic maturity beyond tool lists.
:::

## 4. Active Recall Quizzes

::: quiz Q1: Mixed Drill
Journey-vs-empathy-map pick rule (one line!):
(A) Always both fully (budget-blind maximalism!)
(*B) Temporal pain (queues, waits, flows!) → journey first; inner-life puzzle (motives, emotions!) → empathy map first; both when budget allows (they cross-feed!)
(C) Coin flip
(D) Empathy maps obsolete journeys
::: explanation
Pain-type routing (time-shaped vs mind-shaped!) matches tool affordances (curves vs quadrants!). Diagnostic routing (symptom → instrument!) beats ritual completeness — match, don't maximalise.
:::

::: quiz Q2: Mixed Drill
Success-without-non-goals risks:
(A) Nothing (goals suffice!)
(*B) Scope entropy (adjacent appetites attach mid-project — kitchen rebuilds join queue apps!; unnamed edges invite drift!) — boundary-first scoping always
(C) Slower teams
(D) Fewer ideas
::: explanation
Entropy defence (named outs repel scope cousins!) — non-goals as repellent (stated early, cited often!). Boundary-hygiene (outs listed with ins!) is the focus preservative.
:::

::: quiz Q3: Mixed Drill
Member-checking scheduled *when* in a sprint?
(A) End of project (post-mortem archaeology!)
(*B) Per-artefact, same-sprint (maps verified before POVs built on them! — error-compound prevention: unvalidated layers poison upper layers!)
(C) Never (trust facilitators!)
(D) Only for personas
::: explanation
Layer-gated validation (verify foundations before building!) prevents error compounding (fiction-based POVs beget fiction products!). Validation cadence (per-layer gates!) structures sprint honesty.
:::
